需求分析：Wanchain EVM 跨链与客服 Agent

版本 0.1 · 2026-11-10 · 读者是第一次做 Agent 的开发者 · 配合 工作安排 使用

三件事先记住 助手只办理 EVM 链上的 WanBridge 资产跨链，以及根据官方文档回答问题。交易由用户自己的钱包签名。程序任何地方都不读取、不保存、不索要私钥或助记词。

1. 要做成什么

做一个中文网页助手。用户用自然语言问 Wanchain 的用法，助手根据官方文档回答，并给出文档链接。用户要做跨链时，助手问清楚链、代币、数量和地址，查官方接口得到额度和手续费，等用户在页面上点确认，再向 WanBridge 要一笔待签名交易，交给 MetaMask 签名并发送，之后用交易哈希查询进度。

框架用 LangGraph。客服走检索增强生成（RAG）。跨链走工具调用（tool calling）：模型只负责理解句子和决定下一步问什么，查币对、算费用、生成交易、查状态都由你写的 Python 函数执行。

工期（按本需求的范围） 新手、每天大约 6 小时：9 个星期，43 个工作日。已经会写 Python、还没做过 LangGraph：大约 6 周。每天只有 2 小时：大约 4 个月。熟练且做过 LangGraph 和 Web3 的人：4 到 6 周。明细在第 6 节，每天做什么见工作安排。

2. 本版范围

要做

  • 网页里中文多轮对话。英文问题也能答。
  • 判断这句话是在问文档、要发起跨链，还是要查一笔已有交易。
  • 用官方文档做客服，答案带链接。文档里没有的就说没有。
  • 只办理下面 8 条 EVM 链之间、WanBridge 支持的币对。
  • 查询额度、手续费，用普通人能看懂的小数展示。
  • 缺参数就追问。参数齐了先给确认卡，用户点确认后才生成交易。
  • ERC20 授权不足时，先让钱包做 approve，再发跨链交易。
  • 用源链交易哈希查询状态，并解释含义。

本版不做

  • XFlows、QUiX、跨链兑换。用户问到时，说明本助手不能办理，并指向官网。
  • 非 EVM：比特币、莱特币、狗狗币、瑞波、艾达、波卡、Solana、Sui、Tron 等。
  • Circle CCTP 单独路径。文档可以解释它是什么，不能发起。
  • 服务端签名、托管资产、保存助记词。
  • 节点部署、质押操作、NFT 跨链。
  • 账号系统、人工工单后台、生产级运维。

3. 名词

后面文档直接用这些词。第一次读可以停在这里，每个词用自己的话再说一遍。

词在本项目里的意思
Agent能根据对话决定下一步的程序。这里下一步是查文档、问用户，或调用桥的接口。
LangGraph用「状态 + 节点 + 连线」把对话流程写成图。节点是一段 Python，连线决定接下来去哪个节点。
State这一次对话记住的东西：历史消息、已经填好的链和金额、用户有没有点确认。
Tool calling模型输出「请调用某个函数、参数是这些」。真正发 HTTP 请求的是你的代码，不是模型。
RAG先从文档库找出相关段落，再让模型只根据这些段落回答。
Embedding把一段文字变成一串数字，用来比较两段话像不像。客服检索靠它。
Interrupt图先停住，等用户点确认或取消，再继续。生成交易前必须停一次。
EVM用和以太坊相同的地址格式（0x 开头、40 位十六进制）和同类钱包签名的链。MetaMask 能管这些链。
chainTypeWanBridge 给链起的短名，例如 ARETH 是 Arbitrum。调接口时用它，或用文档表格里的内部 Chain ID，两者不要混在同一次请求里。
tokenPair一条「从某链某代币到另一链某代币」的记录。全库 300 条以上，而且双向都算支持。
原生币这条链自己的 gas 币，例如 ETH、WAN、BNB。接口里代币地址写成 40 个 0。
ERC20合约代币，例如 USDC。转之前，用户要先授权（approve）桥合约能动多少。
decimals代币小数位。USDC 在 Arbitrum 上常常是 6 位，在 BNB Chain 上常常是 18 位。同一符号两边可以不同。
最小单位不带小数点的整数。6 位小数的 1 USDC = 1000000。额度接口返回的是最小单位。
networkFee用源链原生币支付的网络费。
operationFee从被跨链的那种代币里扣的操作费。
lockHash用户在源链上发出跨链交易后的交易哈希。查状态用它。
redeemHash目标链上到账交易的哈希。状态成功后才会有。

4. 谁在用、干什么

本版只有一种用户：会用 MetaMask、想问问题或转一笔 EVM 资产的人。没有管理员后台。

场景用户说的话助手要做到
S1 问用法「跨链一般要多久？」「WAN 是什么？」用文档段落回答，附上链接。文档没有就直说没有。
S2 发起跨链「把 20 个 USDC 从 Arbitrum 转到 BNB Chain，收到这个地址。」查到唯一币对和费用。缺地址或金额就问。展示确认卡。确认后给出待签名交易，网页调起 MetaMask。
S3 币名不清楚「转 USDC 到 Polygon。」发现源链没说、或有多条 USDC，列出候选，让用户选，不猜。
S4 查进度粘贴一个 0x 开头的哈希，或说「我那笔到了吗」。有哈希就查状态并解释。没有就问哈希。Processing 时告诉用户过几分钟再查。

5. 系统怎么串

浏览器负责聊天和签名。Python 服务负责对话图和调用 Wanchain。模型服务只看见文字和工具参数，看不见私钥。私钥不出 MetaMask。

用户浏览器 聊天记录 + 确认按钮 + MetaMask | | HTTPS，只传文字、确认动作、待签名交易 v FastAPI | v LangGraph 分类 → 客服节点（检索文档再回答） → 填槽节点（调用只读工具） → 确认中断（停住） → 生成交易节点（createTx，必须已确认） → 状态节点 → 安全拒绝节点 | +-- 本地向量库（官方文档切片） +-- bridge-api.wanchain.org（币对、费用、createTx、状态）

图的状态里要有的字段

  • messages：对话历史。
  • intent：support、bridge、status、refuse 之一。
  • draft：源链、目标链、符号、数量、付款地址、收款地址、选中的 tokenPair、报价。
  • user_confirmed：只有用户点了确认按钮才变成 true。模型说「用户同意了」不算。
  • last_tx：最近一次 createTx 的结果和 lockHash。
  • citations：这次回答用到的文档链接。

7. 功能说明

F1 网页对话

一个页面：上面是消息，下面是输入框。助手消息里可以出现确认卡（确认、取消两个按钮）和「查询状态」按钮。技术上用 FastAPI 提供接口，页面用普通 HTML 和 JavaScript，不必先学 React。

  • 接口 POST /chat：传入会话 id 和用户文本，返回助手文本、可选的确认卡、可选的待签名交易。
  • 接口 POST /chat/confirm：传入会话 id 和 confirm 或 cancel。
  • 接口 POST /chat/txhash：钱包发出后，把 lockHash 交回这一会话。
  • 会话存在服务端内存或本地 sqlite。本版单机使用，不做登录。

F2 意图路由

每句用户话先经过分类节点。分类只看当前句子和已有 draft，不调用桥。

意图典型句子去向
support怎么用、是什么、要多久、手续费规则客服节点
bridge转、跨、桥、从 A 到 B填槽节点
status句子里有 66 位十六进制哈希，或在问上一笔到了没有状态节点
refuse助记词、私钥、要你代签、非 EVM、XFlows 办理安全节点或固定说明

一句话同时在问进度又要新转一笔时，先处理状态，并告诉用户新的跨链等这一笔说完再开始。

F3 客服 RAG

  1. 按第 9 节的清单把文档下载成 Markdown。
  2. 按标题切开，每块大约 500 到 900 个中文字符的量（英文按单词计，大约 180 到 320 个词）。每块记下标题和原始 URL。
  3. 用多语言向量模型写入本地 Chroma。文档是英文、问题是中文，所以要用多语言模型，推荐 BAAI/bge-m3。电脑内存不够就改用 intfloat/multilingual-e5-base，在配置里写死一个，两处用同一个。
  4. 每次提问取最相关的 4 块。模型只能根据这 4 块回答。回答末尾列出标题和 URL。
  5. 4 块都和问题无关时，回复「官方文档里我没有找到这一点」，不要用常识补。

客服可以解释 XFlows、比特币桥、CCTP 是什么，只要文档里有。解释结束时加上一句：本助手不能替你发起这些操作。

F4 安全拒绝

在调用模型之前用规则扫描用户输入。命中则不把原文送给模型，会话里只留「用户粘贴了敏感内容，已丢弃」。

  • 12 个或 24 个英文单词连在一起，且像助记词。
  • 长度为 64 的十六进制，并且用户把它叫作私钥、private key、secret。
  • 用户要求把助记词发给客服，或要求助手保管资产。

固定回复：不要把助记词或私钥发给任何人，包括这个助手。Wanchain 官方人员不会先私聊你。请立刻停止，并在钱包里确认没有泄露。需要帮助时自己打开 Wanchain 官方 Telegram 支持，不要点陌生人发来的链接。

F5 币对查询

只读接口：

  • GET https://bridge-api.wanchain.org/api/tokenPairsHash
  • GET https://bridge-api.wanchain.org/api/tokenPairs

先取 hash。和本地缓存相同就用缓存，不同就重新下载，写到 data/pairs_cache.json。查找时：

  1. 把用户说的链名翻译成允许名单里的 chainType。翻译不了就问。
  2. 符号忽略大小写。
  3. 一条记录是双向的。Arbitrum→BNB 和 BNB→Arbitrum 只要链和代币地址对得上，就算支持。方向以用户要走的方向为准，去读对应那一侧的 decimals。
  4. 结果 0 条：说明当前桥不支持这条路径。
  5. 结果 1 条：写入 draft。
  6. 结果多于 1 条：把链名、代币地址、decimals 列给用户选。禁止模型自己挑一条。

F6 额度与手续费

选定唯一币对后调用：

GET https://bridge-api.wanchain.org/api/quotaAndFee
    ?fromChainType=ARETH
    &toChainType=BNB
    &tokenPairID=453
    &symbol=USDC

也可以分开调用 /api/quota 和 /api/fee。本版用合并接口即可。

  • minQuota、maxQuota 是源代币的最小单位。展示前除以 10 的 decimals 次方。
  • networkFee.isPercent == false：value 是源链原生币的最小单位（wei）。18 位小数时，7000000000000000 展示为 0.007。
  • networkFee.isPercent == true：value 是比例，0.006 表示 0.6%，再受 minFeeLimit 和 maxFeeLimit 约束。这两个限也是最小单位。
  • operationFee 规则相同，但币种是正在跨的那种代币。
  • 用户数量小于最小额度，或大于最大额度，就停下来说明，不进入确认。

给用户看的句子要像这样：从 Arbitrum 转 20 USDC 到 BNB Chain。网络费大约 0.007 ETH（在源链用原生币付）。操作费按 0 计算。预计到账 20 USDC。当前额度 0 到 5000 USDC。请核对收款地址。

F7 填槽与校验

一笔草稿要齐这 6 项才给确认卡：源链、目标链、代币符号、数量（十进制字符串）、付款地址、收款地址。付款地址默认等于钱包当前账户，用户也可以指定。两边地址都要是合法的 EVM 地址，用 eth_utils 校验并改成校验和形式再展示。

一次只追问一个缺失项，按这个顺序：源链、目标链、代币、数量、收款地址、付款地址。用户说「改成 10」时只替换数量，其他保留。

数量用字符串保存，不要用浮点数。请求 createTx 时 amount 就是这个十进制字符串，例如 "0.01"，不要自己乘成 wei。

F8 确认

确认卡固定包含：源链和目标链的中文名、代币符号、两边合约地址、数量、预计到账、networkFee 和 operationFee 的中文说明、付款地址、收款地址。按钮只有「确认」和「取消」。

取消把 user_confirmed 保持 false，草稿可以留着让用户改。确认后才允许进入 F9。

硬规则写在 Python 里，不写在提示词里：create_tx() 开头检查 user_confirmed is True。否则抛出错误，不发 HTTP。

F9 生成待签名交易

使用普通接口，不用合作方接口 createTx2。

POST https://bridge-api.wanchain.org/api/createTx
Content-Type: application/json

{
  "fromChain": "ARETH",
  "toChain": "BNB",
  "fromToken": "0x源代币地址",
  "toToken": "0x目标代币地址",
  "fromAccount": "0x付款地址",
  "toAccount": "0x收款地址",
  "amount": "20"
}

fromChain 和 toChain 都用 chainType，不要混用内部 Chain ID。原生币地址用 0x0000000000000000000000000000000000000000。

成功时读取：

  • data.tx：交给钱包的 from、to、value、data。
  • data.chainId：钱包要切换的网络号。
  • data.receiveAmount：预计到账，展示给用户。
  • data.approveCheck：有这个字段就走 F10。
  • data.feeAndQuota：可用来核对 F6 的报价。两边不一致时，以这一份为准再让用户看一眼。

success 为 false 时，把接口返回的原因原样告诉用户，不改写成「已经成功」。

F10 ERC20 授权

approveCheck 里有 from、token、to（被授权的桥合约）、amount（最小单位）。页面用公共 RPC 读这个代币的 allowance(from, to)。余额授权小于 amount 时，先发一笔 approve，等它上链，再发 data.tx。原生币没有授权这一步。

授权金额用接口给的 amount，不要改成无限大授权。本版不做这个优化。

F11 MetaMask 签名发送

  1. 请求账户。用户拒绝就停。
  2. 如果当前网络不是 data.chainId，请求切换。钱包里没有这条网络时，按官方网络资料添加。Wanchain 的资料页：Network information。RPC 地址从这一页抄，不从论坛抄。
  3. 当前账户必须等于 tx.from。不等就提示用户在钱包里换账户，不代发。
  4. 需要授权就先发 approve。
  5. eth_sendTransaction 发送 tx。gas 相关字段留给钱包估算，请求里没有的不要自己填 0。
  6. 拿到 lockHash 后显示出来，并写入会话，供 F12 使用。

第 7 周之前不要做签名。前几周把 tx JSON 打印出来，和官方示例 bridge-api-demo-ui 对照字段。示例源码：wandevs/bridge-api-demo-ui。

F12 状态查询与解释

GET https://bridge-api.wanchain.org/api/status/{lockHash}。lockHash 是源链或目标链上的交易哈希。解释用固定句子，模型只能补充文档里的到账时间说明，不能发明新状态。

status对用户说
NotFound桥还没有索引到这笔交易。若刚刚发送，等几分钟再查。哈希请核对是不是源链那一笔。
Processing正在处理。耗时取决于两条链的确认速度，以太坊会比 BNB Chain 慢。现在不要重复发起同一笔。
Trusteeship交易信息需要人工处理。本助手不能代办。请到官方支持渠道，并准备 lockHash。
Refund这笔被退回了。sendAmount 和 receiveAmount 按两边 decimals 换算后说明。常见原因包括地址触发风控。退回不等于在目标链到账。
Success已完成。给出 redeemHash，并说明到账数量。sendAmount 与 receiveAmount 的差额是手续费。

sendAmount 和 receiveAmount 是最小单位，要按源代币和目标代币各自的 decimals 换算后再显示。

页面提供「再查一次」按钮。服务端不要在一次 HTTP 请求里循环等到 Success。跨链可能要好几分钟。

F13 会话记忆

用 LangGraph 的 checkpointer，按会话 id 保存状态。至少要记住 draft 和上一笔 lockHash。新开会话 id 时从空白开始。

F14 日志与评测

日志记录：时间、会话 id、意图、工具名、工具参数、接口是否成功、错误文本。不记录用户粘贴的疑似助记词原文。

评测文件放在 eval/：

  • support_questions.jsonl：30 题。每题有期望要点和期望文档关键词。通过标准：至少 24 题的答案包含正确来源，且没有把库外内容说成文档原文。
  • bridge_scripts.jsonl：15 段多轮对话。通过标准：至少 12 段在用户确认之前，测试桩没有收到 createTx。地址错误、超额、非 EVM、同名币各至少 1 段。

8. 跨链规则

这些规则由代码执行。提示词里可以复述，但不能代替代码。

  1. 允许名单之外的 chainType，不调用 createTx。
  2. user_confirmed 不为 true，不调用 createTx。
  3. 收款地址校验失败，不调用 createTx。
  4. 数量不在额度内，不调用 createTx。
  5. 找不到唯一币对，不调用 createTx。
  6. 单笔数量超过配置里的 MAX_AMOUNT_HUMAN 时，即使额度允许也拒绝。初值建议：稳定币 100，原生币 0.05。这是练习限额，写在 config.py，总验收用小额。
  7. 模型不能修改 toAccount。展示给用户的地址必须和请求体里的字符串完全一致。

10. 安全

资产损失是这个项目的主要风险 收款地址填错、选错链、重复发送，都无法靠模型事后补救。所以确认卡、限额、代码里的拦截比提示词重要。
  • 环境变量放 API key。仓库里只提交 .env.example，.env 进 gitignore。
  • 日志和错误上报里不出现助记词、私钥、完整的未签名 data 可以留，因为它不是密钥。若拿不准，未签名交易只在内存里交给前端，不写文件。
  • 前端不把私钥相关请求发到你的服务器。MetaMask 的 eth_sendTransaction 只在浏览器里调用。
  • 练习阶段用测试网。测试网没有对应币对时，主网只在第 9 周用低于限额的数量做一次，并在确认卡上再次读出地址。
  • 别人私聊提供「客服链接」时，助手的固定说法是：官方不会先私聊。频道是 t.me/WanchainSupport。

11. 其他要求

  • 界面文字用中文。文档原文是英文时，回答用中文，专有名词保留英文。
  • 模型通过环境变量配置：LLM_BASE_URL、LLM_API_KEY、LLM_MODEL。选一个支持工具调用的聊天模型。换供应商时只改变量。
  • Python 3.11 或 3.12。依赖写进 requirements.txt 并锁住你实测过的版本。
  • 桥接口超时设为 20 秒。失败时把 HTTP 状态和响应正文的前 500 字返回给日志，给用户一句「桥接口暂时失败，请稍后再试」。
  • 单机运行即可：uvicorn 加本地页面。本版不部署到公网，因此不做登录和限流。若以后放到公网上，先加限流再开放，避免被人拿去刷 createTx。

13. 总验收

第 9 周照着做一遍。每一项都要在浏览器里真实点过，不能只看单元测试。

  1. 问「WanBridge 是什么」，回答有中文说明和官方文档链接。
  2. 问一个文档里显然没有的内部问题，例如「我的工号是多少」。助手表示不知道。
  3. 把一组假的 12 个单词当助记词粘贴进去。助手警告，日志里没有这 12 个词。
  4. 说「把 BTC 从比特币转到以太坊」。助手拒绝办理，并给出官网。
  5. 说「从 Arbitrum 转 USDC 到 BNB Chain」，不给数量。助手只问数量，不调用 createTx。
  6. 给一个非法地址。助手指出地址不对，不出现确认卡。
  7. 参数齐全且低于限额。出现确认卡，地址和你输入的逐字相同。
  8. 点取消。网络面板里没有对 createTx 的请求。
  9. 重新确认。服务器调用 createTx 成功，MetaMask 弹出。拒绝签名时，页面停住，没有伪造哈希。
  10. 在测试网或限额内的主网签一笔。页面拿到 lockHash，状态先是 NotFound 或 Processing，之后能再查。
  11. 若是 ERC20 且授权不足，钱包先弹出 approve，再弹出跨链交易。
  12. 拿一个已知成功的公开哈希（文档示例或你自己的上一笔）查询，解释和状态字段一致，金额不是一长串未换算的整数。
  13. 客服评测至少 24/30。跨链剧本至少 12/15 在确认前没有 createTx。
